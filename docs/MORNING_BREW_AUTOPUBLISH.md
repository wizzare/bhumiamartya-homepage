# Morning Brew Auto-Publish

Automates publishing the daily "Morning Brew" article (generated by Gemini Spark and saved
to Google Drive) onto `bhumiamartya.my.id`, with no new database, CMS, or service.

Scope: **Morning Brew only**. Senja & Cerita and any other content automation are out of
scope for this integration.

## Architecture

```
Gemini Spark (05:00 WIB)
  -> saves "Morning Brew - YYYY-MM-DD" to a fixed Google Drive folder
Google Apps Script (~05:30 WIB, daily trigger)
  -> finds TODAY's file only (never "latest file", never yesterday's)
  -> reads its content + title
  -> POST https://bhumiamartya.my.id/api/content/morning-brew
     Authorization: Bearer <MORNING_BREW_PUBLISH_SECRET>
Vercel serverless function (api/content/morning-brew.mjs)
  -> validates the shared secret + payload
  -> writes to the SAME Firestore `articles` collection the site already reads from
     (source: "bhumi", category: "Morning Brew", status: "published")
  -> idempotent by design: doc id = morning-brew-<date>, so a re-send never duplicates
Website
  -> article appears at /articles/<slug>/, in /articles/ listing, and in /sitemap.xml
     automatically, using the existing article rendering/SEO pipeline
```

No new database, no new CMS, no new Vercel project, no queue, no Cloud Function/Worker.
This reuses the homepage repo's existing GCP Workload Identity Federation → Firestore
client (`lib/gcp-oidc.mjs`), the same one already used to read published articles.

## Google Drive folder

Morning Brew files live in this existing folder — no new folder is created:

- Folder ID: `1Vm8kFWCJZuVmERtnHmi3_bleN8QQvNU0`
- Expected file name: `Morning Brew - YYYY-MM-DD` (e.g. `Morning Brew - 2026-09-18`)
- Google Docs is the primary supported format; plain text/other blob files are read as a
  fallback. The Apps Script also tolerates a file name that merely *contains* the date, in
  case Gemini Spark's naming drifts — but it will only ever match **today's** date, never
  "whatever file is newest."

## API endpoint

`POST /api/content/morning-brew`

File: `api/content/morning-brew.mjs` · write logic: `lib/content/firestore-writer.mjs`

### Auth

```
Authorization: Bearer <MORNING_BREW_PUBLISH_SECRET>
```

Compared with `crypto.timingSafeEqual`. Missing/invalid header, wrong secret, or the env
var not being configured on the server all return `401`/`503` — never a silent write.

### Request body

```json
{
  "title": "Ketika Kamu Capek Menjadi Kuat Terus",
  "content": "Isi Morning Brew hari ini...",
  "date": "2026-09-18",
  "source": "google-drive"
}
```

| field   | required | notes                                                              |
|---------|----------|---------------------------------------------------------------------|
| title   | yes      | 1–300 chars                                                         |
| content | yes      | plain text or simple markdown-ish text (`#`/`##` headings, `- ` lists, blank-line paragraphs, `![alt](url)` images) |
| date    | yes      | `YYYY-MM-DD`, must be a real calendar date, Asia/Jakarta local date |
| source  | no       | free text, defaults to `google-drive`; stored as `sourceChannel`, does **not** overwrite the existing `source: "bhumi"` field that the site's article queries filter on |
| excerpt | no       | if omitted, auto-derived from the first ~160 chars of `content`     |
| coverImageUrl | no | optional cover image URL                                       |
| dryRun  | no       | `true` validates auth + payload and returns a preview slug **without** writing to Firestore — useful for connectivity testing |

### What the server sets automatically

`slug` (from `title`, collision-safe), `category: "Morning Brew"`, `status: "published"`,
`source: "bhumi"` (existing convention, required for the article to show up anywhere on the
site), `sourceId: "morning-brew-<date>"`, `publishedAt`, `createdAt`, `updatedAt`,
`seoTitle`, `seoDescription`, `readingTimeMinutes`, `tags: ["morning-brew"]`.

### Responses

| case                          | status | body                                                             |
|--------------------------------|--------|--------------------------------------------------------------------|
| new article published          | 201    | `{"success":true,"status":"published","slug":"...","url":"..."}`  |
| same date sent again           | 200    | `{"success":true,"status":"already_published","slug":"...","url":"..."}` |
| dry run                        | 200    | `{"success":true,"status":"dry_run","slug":"...","message":"..."}` |
| missing/invalid secret         | 401    | `{"success":false,"code":"UNAUTHORIZED", ...}`                    |
| missing title/content/date     | 400    | `{"success":false,"code":"INVALID_TITLE"/"INVALID_CONTENT"/"INVALID_DATE", ...}` |
| wrong HTTP method              | 405    | `{"success":false,"code":"METHOD_NOT_ALLOWED", ...}`               |
| server not configured          | 503    | `{"success":false,"code":"CONTENT_SERVICE_UNAVAILABLE"/"PUBLISH_NOT_CONFIGURED", ...}` |
| Firestore/write failure        | 503    | `{"success":false,"code":"PUBLISH_FAILED", ...}` (no internal detail leaked) |

### Anti-duplicate (two layers)

1. **Apps Script**: after a successful publish it stores
   `PUBLISHED_MORNING_BREW_YYYY_MM_DD=true` in Script Properties and skips re-sending for
   that date on subsequent trigger runs.
2. **Website (authoritative)**: the Firestore document id for a Morning Brew article is
   always `morning-brew-<date>`. The API checks for that doc first; if it already exists it
   returns `already_published` and writes nothing. `docRef.create()` is used for the actual
   write (fails on a race instead of overwriting), so even concurrent requests can't create
   two articles for the same date. This is the one that actually prevents duplicates if the
   Apps Script side is ever reset or run from two places.

### Article page / SEO

No new routing was added. Morning Brew articles are plain rows in the existing `articles`
Firestore collection, so they automatically:
- appear in `/articles/` (via `GET /api/bhumi-articles`)
- render at `/articles/<slug>/` (via the existing `api/article-page.mjs` +
  `lib/content/render-article.mjs`, which already builds canonical URL, Open Graph,
  Twitter Card, and `Article` JSON-LD schema tags)
- appear in `/sitemap.xml`
- show a "Morning Brew" category badge (existing UI just prints whatever `category` is)

## Apps Script setup

Full script: [`docs/apps-script/MorningBrewPublisher.gs`](./apps-script/MorningBrewPublisher.gs)
— copy-paste ready.

1. Go to [script.google.com](https://script.google.com), **New project**, paste the
   contents of `MorningBrewPublisher.gs` in, replacing the default file.
2. Store the secret (never commit it to source):
   - In `setupSecret_()`, temporarily replace `PASTE_YOUR_MORNING_BREW_PUBLISH_SECRET_HERE`
     with the real secret value (ask the operator for it, or read it from the Vercel
     project's environment variables — it's stored there as `MORNING_BREW_PUBLISH_SECRET`).
   - Run `setupSecret_` once (function picker at the top of the editor → select it → ▶ Run).
     Accept the Drive + external request authorization prompt the first time.
   - Immediately delete the literal secret from the source and save again.
3. Verify connectivity without publishing anything: run `testConnection`. Check
   **Executions** (left sidebar) → should log `status=200` with `"status":"dry_run"`.
4. Install the daily trigger: run `createDailyTrigger` once. This creates a time-based
   trigger for `publishMorningBrew` at ~05:30 Asia/Jakarta, and is safe to re-run (it clears
   any prior trigger for the same function first, so you never get duplicates).
5. (Optional) Run `publishMorningBrew` manually once today, after Gemini Spark has actually
   produced today's file, to confirm the end-to-end flow.

Apps Script time-based triggers aren't second-precise — "~05:30" (a few minutes' slack) is
expected and fine, since it only needs to run after Gemini Spark's 05:00 generation.

### Behavior details

- **Today only, never "latest file"**: the script computes today's date in `Asia/Jakarta`,
  looks for `Morning Brew - YYYY-MM-DD` by exact name first, then falls back to scanning the
  folder for any file whose name *contains* that exact date string. If nothing matches, it
  logs `Morning Brew YYYY-MM-DD belum ditemukan.` and exits — it will never fall back to
  yesterday's file or "the newest file in the folder."
- **Title detection**: first heading-style paragraph (Title/Heading 1/Heading 2) inside the
  Google Doc if present, otherwise the file name with the `Morning Brew - YYYY-MM-DD` prefix
  stripped.
- **Google Docs first**: `DocumentApp.openById(...).getBody().getText()` is the primary
  path; other file types fall back to reading the raw blob as UTF-8 text.
- **Never deletes or edits the Drive file.** Publish status is tracked only in
  `PropertiesService.getScriptProperties()`.
- **Failure handling**: any non-2xx/non-`success:true` response from the API is logged (HTTP
  status + full response body) and the run is *not* marked published, so the next scheduled
  or manual run retries automatically. The website's own `morning-brew-<date>` doc-id dedup
  means a retry is always safe even if the first attempt actually succeeded but the Apps
  Script failed to see the response.

## Manual testing

Replace `<SECRET>` with the real value from Vercel.

```bash
# 1. Dry run (no write) — verifies secret + payload shape
curl -i -X POST https://bhumiamartya.my.id/api/content/morning-brew \
  -H "Authorization: Bearer <SECRET>" \
  -H "Content-Type: application/json" \
  -d '{"title":"Test","content":"Isi tes.","date":"2026-09-18","dryRun":true}'

# 2. Publish a real test article
curl -i -X POST https://bhumiamartya.my.id/api/content/morning-brew \
  -H "Authorization: Bearer <SECRET>" \
  -H "Content-Type: application/json" \
  -d '{"title":"Ketika Kamu Capek Menjadi Kuat Terus","content":"Isi Morning Brew hari ini.","date":"2026-09-18","source":"google-drive"}'
# Expect: 201, {"success":true,"status":"published","slug":"...", "url":"..."}

# 3. Send the exact same date again -> must NOT duplicate
curl -i -X POST https://bhumiamartya.my.id/api/content/morning-brew \
  -H "Authorization: Bearer <SECRET>" \
  -H "Content-Type: application/json" \
  -d '{"title":"Ketika Kamu Capek Menjadi Kuat Terus","content":"Isi berbeda.","date":"2026-09-18"}'
# Expect: 200, {"success":true,"status":"already_published", ...}

# 4. Wrong secret
curl -i -X POST https://bhumiamartya.my.id/api/content/morning-brew \
  -H "Authorization: Bearer wrong-secret" \
  -H "Content-Type: application/json" \
  -d '{"title":"Test","content":"Isi tes.","date":"2026-09-18"}'
# Expect: 401

# 5. Missing content
curl -i -X POST https://bhumiamartya.my.id/api/content/morning-brew \
  -H "Authorization: Bearer <SECRET>" \
  -H "Content-Type: application/json" \
  -d '{"title":"Test","date":"2026-09-18"}'
# Expect: 400

# 6. Open the published article publicly
curl -i https://bhumiamartya.my.id/articles/ketika-kamu-capek-menjadi-kuat-terus/
```

Automated tests covering the same cases live in `tests/content-morning-brew.test.mjs`
(HTTP handler) and `tests/morning-brew-writer.test.mjs` (Firestore write logic, anti-dupe,
slug collisions), run via `npm run test:engines`.

## Troubleshooting

- **`Morning Brew YYYY-MM-DD belum ditemukan.` every day** — Gemini Spark's 05:00 run may be
  late, or the file name doesn't contain today's date. Check the Drive folder directly.
- **API returns 401** — the secret in Script Properties doesn't match Vercel's
  `MORNING_BREW_PUBLISH_SECRET`. Re-run `setupSecret_()` with the correct value.
- **API returns 503 `CONTENT_SERVICE_UNAVAILABLE`** — `GCP_PROJECT_ID` (or one of the other
  four `GCP_*` WIF env vars) isn't set on the Vercel project for that deployment target.
- **API returns 503 `PUBLISH_FAILED`** — check the Vercel function logs for
  `[morning-brew] publish failed: ...`. The most likely cause is the GCP service account
  behind `GCP_SERVICE_ACCOUNT_EMAIL` not having Firestore **write** permission (it may only
  have been granted read access so far, since this integration is the first write path added
  to this repo) — grant it `roles/datastore.user` (or equivalent) on the Firestore project in
  Google Cloud IAM.
- **Article doesn't show on `/articles/`** — the listing endpoint only fetches the 40 most
  recently-created docs from Firestore and sorts by `publishedAt` (pre-existing behavior,
  unrelated to this change); check the article exists via
  `GET /api/bhumi-article?slug=<slug>` first.
- **Trigger seems to have stopped firing** — open the Apps Script project → **Triggers**
  (clock icon) → confirm `publishMorningBrew` still has an active daily trigger; re-run
  `createDailyTrigger()` if not (it safely replaces any existing one).
